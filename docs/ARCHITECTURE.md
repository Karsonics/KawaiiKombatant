# Architecture

Status: current implementation plus explicitly labeled design direction. Verify behavior in code before relying on this note.

## Current implementation

Kuro is a single Python application with CLI, API, voice, storage, and avatar modules:

- `bot_main.py` selects direct CLI, WebSocket CLI, voice client, or avatar client modes.
- `server/kuro_api.py` serves the web UI and FastAPI/WebSocket endpoints. It constructs a module-level `KuroEngine` during import. Synchronous engine work is run through an executor in the WebSocket path.
- `server/kuro_engine.py` coordinates LLM generation, conversation history, memory extraction, mood calculation, summarization, and TTS. The engine streams text from the provider but invokes TTS inline as sentences are processed.
- `server/llm/base.py` defines a small provider protocol; `openai_compatible.py` adapts OpenAI-compatible chat completions for configured providers such as Ollama, OpenAI, OpenRouter, and custom endpoints. Provider streaming yields text fragments.
- `server/process/storage/mysql_storage.py` stores conversations, session state, per-session summaries, and user preference JSON in MySQL. The engine falls back to in-memory/no-persistence behavior when database initialization fails.
- `server/process/storage/markdown_memory.py` provides Markdown memory storage with per-user files, validated YAML frontmatter, CRUD/filter operations, and deterministic query matching. During normal startup, `KuroEngine` initializes this store using the explicitly configured vault path and validated effective user ID, exposes its availability status, and continues in degraded mode if it cannot initialize. Dry-run startup skips the store. On each turn, active facts, preferences, and experiences matching the latest user message are added as bounded reference context. Automatic capture uses the configured lightweight extraction model and saves only strictly validated exact quotes after local sensitivity, duplicate, and conservative conflict checks. MySQL-backed `UserMemory` remains active for existing preference/fact behavior.
- `server/process/tts_func/` contains a manager and GPT-SoVITS/F5-TTS implementations. F5-TTS may be unavailable depending on its separate service/dependencies. `voice/` and `server/process/asr_func/` implement microphone, VAD, Whisper transcription, and voice-client paths.
- `avatar/` connects to VTube Studio and maps mood updates to configured hotkeys/idle actions.

The code has some interfaces and adapters, but orchestration and several subsystem concerns remain in `KuroEngine`. Importing the API module has initialization side effects. The existing arrangement should not be mistaken for a fully decoupled architecture.

## Runtime and persistence notes

- LLM configuration is read from `configs/bot_config.yaml`; a legacy `ollama` section is supported by the engine. The provider adapter uses the OpenAI SDK protocol.
- MySQL credentials/settings are expected in the ignored local file `configs/database_config.yaml`; no tracked template for it is present. Without usable database access, the engine logs a warning and continues without persistence.
- ASR settings are in `configs/asr_config.yaml`; VTube Studio settings are in `configs/vtube_config.yaml`. TTS provider routing is configured in `bot_config.yaml`; GPT-SoVITS details and voice references are in `sovits_config.yaml`.
- WebSocket and CLI behavior, message formats, and configuration are observable contracts. Inspect callers and tests before changing them.

## Conversation context and summaries

- Working conversation context is the recent transcript slice loaded for the current session. MySQL remains the transcript source of truth.
- Every chat-generation request starts with the configured `character.system_prompt` as a dedicated system message, even when the persisted system row is outside the transcript window. Other persisted system-role transcript rows are excluded from generation. Session summaries and both legacy and Markdown user memory are supplied as explicitly marked user-role reference data, so user-derived content does not gain system-instruction authority.
- When at least `chat.summarization_threshold` uncheckpointed, completed user/assistant messages are available, `KuroEngine._maybe_summarize` supplies the previous cumulative summary plus the new segment to the summarization model. It stores the non-empty result and last summarized message ID together in the existing session-keyed `session_summaries.summary` TEXT column as a versioned JSON envelope; no schema migration is required. Legacy plain-text summary rows remain readable with checkpoint zero and are incorporated the next time a summary is successfully written. Prompt construction reads the summary for the requested session only. New session IDs have no prior summary; resuming a session loads its own summary.
- A successful checkpoint advances only through complete user/assistant segments. A failed/empty model response, failed MySQL write, or compare-and-set conflict leaves the prior summary and checkpoint available for a later attempt. The model receives earlier summary context and only newly checkpointed transcript messages; this reduces repeated summarization, though the model can still omit details when it produces a cumulative summary.
- A process-wide, idle-evicted per-session reentrant lock covers each complete `process_message()` turn from user transcript write through assistant write and summary attempt. Same-session turns in one process cannot interleave; different sessions remain independent. MySQL additionally uses a byte-exact conditional update against the raw summary value read before model generation, including legacy plain-text rows. Missing rows use insert-only creation; an existing NULL row uses `UPDATE ... WHERE summary IS NULL`. A losing writer defers its uncheckpointed transcript segment to a later summary attempt and is not reported as a successful save. Turn ordering is not coordinated across multiple Python processes; the built-in API starts one worker, and multi-process sharing of a session is unsupported. Summary CAS still prevents stale summary writes across processes.
- Transcript queries order by `timestamp, id`; limited recent-context queries use descending timestamp and ID, then reverse results to chronological order. The auto-increment message ID makes equal-timestamp ordering deterministic and is also the stable summary checkpoint.
- Summarization uses `llm.summarization_model` when set. For backward compatibility, omitted values fall back to `llm.extraction_model`, then `llm.model`. Personal-information extraction continues to use `llm.extraction_model`.
- Summary generation, retrieval, or persistence failures are logged and treated as missing or unchanged summary context so ordinary conversation can continue. Existing transcripts are unchanged. Session clearing also removes that session's summary.
- User-level `UserMemory` remains responsible for preferences, facts, and other user-level state. Its legacy `conversation_summary` field and any stored values are not migrated or deleted, but the conversation engine no longer reads or writes that field for session summarization.
- `UserMemory.flush()` clears its dirty flag only after a successful save. If connection acquisition or persistence fails, changes remain dirty in memory and a later explicit flush can retry; diagnostics do not include memory values. The no-database engine fallback continues chat without persistence. Pending dirty state is process-local and is lost if the process exits before a successful save; there is no background retry worker.

## Markdown long-term memory — retrieval and capture integrated

- The standalone `MarkdownMemoryStore` requires an explicit vault path and can initialize `README.md` plus `users/<user_id>/` directories containing `profile.md`, `facts/`, `preferences/`, `experiences/`, and `temporary/`.
- During normal startup, Kuro reads the explicitly configured absolute `memory.vault_path` setting; it has no fallback. If it is absent, blank, relative, or unavailable, Markdown memory remains unavailable while chat starts; the health response exposes only an availability status. The single effective `chat.user_id` is validated before startup; omitted IDs retain the existing `default_user` fallback. Dry-run startup skips vault initialization and reports it as unavailable.
- Each memory is an individual Markdown file with validated YAML frontmatter. The storage API supports create, get, list/filter, query search, update, and delete; list skips malformed files and all parseable records sharing a duplicate ID anywhere in the user's memory directories, with filename-only diagnostics.
- Markdown files are the source of truth for long-term personal-memory records. MySQL remains responsible for transcripts, session summaries, operational state, and the existing JSON-backed `UserMemory`; no legacy MySQL memory migration is performed.
- Writes use a same-directory temporary file, flush and `fsync`, then `os.replace`. Updates and deletes require the version token returned by a read, so stale edits are rejected. A process-local lock serializes writes in one process; cross-process locking is not implemented or guaranteed.
- KuroEngine searches active facts, preferences, and experiences against the latest user message, ranks by token overlap, and enforces result and character bounds. An active record with `expires` is eligible only before that UTC instant; at the exact cutoff it is expired. `null` expiry means no cutoff. Search does not update or delete expired records. Malformed records (including malformed expiry metadata) are skipped and reported through diagnostics. Retrieved text is labeled as untrusted reference data.
- `last_confirmed` means the user explicitly reviewed and confirmed the record's content. Retrieval and repeated mentions do not refresh it. The confirmed `confirm_memory <id>` command records the current UTC time and sets epistemic status to `confirmed`; the storage update still uses the record version. Nullable `source_session`, `last_confirmed`, and `expires` can be explicitly cleared by passing `None` to `update_memory`; omitting them preserves existing values.
- Automatic capture uses `llm.extraction_model` when the Markdown store is available and can be disabled with `memory.capture_enabled: false`. Malformed, uncertain, sensitive, and duplicate candidates are rejected. Candidate overlap is not by itself treated as a conflict. A different preference for an overlapping context is held as a review candidate; explicit correction wording is labeled `potential_correction`, while a contradictory statement without such wording is `potential_conflict`. Capture does not alter existing records.
- On-demand `memory_review` combines deterministic pairwise lexical comparisons of stored records with review candidates from the most recent capture in the current process. Expired, archived, or superseded records can be marked potentially outdated. Pending capture candidates are not persisted and disappear after a later capture replaces them or the process restarts. Candidate explanations and IDs are review aids, not semantic verification. Related records are not assumed to conflict. Review does not run on the chat response path or call an LLM.
- Memory and summary values are reference context, not instruction sources. Their user-derived contents are enclosed in an untrusted-reference block in a user-role message; the configured system prompt remains a separate system message. Retrieval, confirmation metadata updates, and review do not change lifecycle status. Changing status through `update_memory()` and deleting through the storage API require `confirmed=True`; clearing and deleting through user-facing commands also require explicit confirmation. No user-facing command automatically archives or supersedes a record, and no automatic merge or correction action is performed.
- Before generation, the engine escapes reference-tag-like strings in all three user-derived sources, then applies one `memory.max_reference_context_chars` budget to the complete untrusted reference message, including escaped content, source labels, separators, and wrapper markers. Escaping is case-insensitive and handles whitespace around the tag name and closing slash. The default is 6000 characters; accepted values are 384–20000, and invalid values fall back to the default with a content-free warning. Sources are prioritized as retrieved Markdown records, the current session summary, then legacy `UserMemory`. Complete sections/records are retained when they fit; otherwise the remaining content is clipped at a line or word boundary and an explicit truncation marker is added. Lower-priority sources may be omitted. This does not alter stored data, the configured character prompt, or transcript turns; the limit counts characters, not model tokens.
- Session summaries are now separate from user-level memory. Markdown retrieval supplies cross-session personal context only; it does not participate in summary generation or storage.

## Proposed design direction — not implemented contracts

These are design ideas for future, separately scoped work; they are not current capabilities or requirements to refactor immediately:

- Add a separately approved human-review workflow before any consolidation candidate can change a record; keep the current review non-destructive and session summaries/operational state in MySQL.
- Gradually separate API transport, conversation orchestration/context, storage, memory, speech events, and avatar control behind explicit interfaces.
- Consider an application factory/lifespan so API initialization does not occur at import time.
- Consider decoupling synthesis/playback from LLM token processing with a bounded asynchronous TTS queue, preserving order and defining cancellation/backpressure behavior. There is no such queue currently.
- If agent tools are introduced, use a bounded dispatcher with narrow schemas, permissions, timeouts, and audit behavior; no agent tool runtime is currently present.
- Evaluate session isolation and shared state concurrency as behavior evolves. Do not assume the current global API engine or user memory is session-isolated.
- Measure actual CPU, RAM, GPU/VRAM, and latency before adding model/resource management behavior.

Any proposal that changes public behavior, persistence/schema, deployment, or subsystem boundaries should state its evidence and trade-offs before implementation.
